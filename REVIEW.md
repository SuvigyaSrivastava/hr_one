# REVIEW.md

Review of the starter `app/main.py`. Every defect below was reproduced by a test in `tests/` that **failed on the starter
(46 of 58 live-API tests failed)** and passes after the fix (`pytest tests` -> 90 passed). The rules helpers were
replaced by a tested pure-function rules engine (section 2 of `app/main.py`, `tests/test_rules.py`).

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Uses the punch-in's own (naive / server-local) clock, not IST. Shift start is built on the wrong zone and date, so every result depends on the server's time zone. | Employee 09:30 shift, punch-in 10:15:59 IST: starter returns 0, expected 45 (`test_punch_in_late_rule[10-15-59-45]`). | `calc_late_minutes` works on tz-aware instants and builds shift start in IST (R1, R2). |
| 2 | `compute_late_minutes` | Grace check is `floor(minutes) > 10`, but the rule is "strictly more than 10:00 *in seconds*". 09:40:01 floors to 10, so it is treated as on time. | 09:40:01 -> starter 0, expected 10 (`test_punch_in_late_rule[9-40-1-10]`). | Compare in whole seconds (`delta > 600`), then floor to minutes from shift start. |
| 3 | `compute_late_minutes` / `punch_in` | No truncation to whole seconds (R1) and no overnight-shift handling: a 22:00-06:00 employee punching in at 01:00 is measured against today's 22:00 and gets the wrong date. | `test_punch_in_overnight_shift_date`, `test_punch_in_truncates_to_seconds`. | `trunc_seconds` at the boundary; `attendance_date` and `shift_start_at` implement the overnight rule (R1). |
| 4 | `compute_work_hours` | `round(float, 2)` is banker's rounding on a binary float, not half-up (R4). | 450 s = 0.125 h: `round` gives 0.12, expected 0.13; 16218 s = 4.505 h gives 4.5, expected 4.51 (`test_work_hours_half_up_not_bankers`). | `Decimal` arithmetic with `ROUND_HALF_UP` (`round_half_up`, `calc_work_hours`). |
| 5 | `compute_overtime` | No 30-minute minimum (R3); end-of-shift is built from the date string on the same calendar day, so overnight shifts are wrong; subtracts an aware IST datetime from a naive `punch_out` -> `TypeError`. | 5 minutes after shift end returns 5 instead of 0; any call with a Mongo datetime raises. | `calc_overtime_minutes`: floor minutes, only if >= 30, shift end on the next day for overnight shifts, all values tz-aware. |
| 6 | `punch_in` | `datetime.fromtimestamp(ms/1000)` uses the **server's local zone** and returns a naive value; the attendance `date` is that local date, not the IST date (R1). `if body.punched_at` treats a value of 0 as "not supplied". | 00:30 IST on 7 Jul was stored under 6 Jul on a UTC server (`test_punch_in_record_shape_and_ist_date`). | `ms_to_dt` (UTC-aware, whole seconds) and `attendance_date` (IST); `is not None` check. |
| 7 | `punch_in` | Unknown `emp_code`: `emp` is `None`, `emp["shift_start"]` raises `TypeError` -> **HTTP 500** (contract: 404). | `POST /attendance/punch-in {"emp_code":"NOPE"}` -> 500 (observed). | Explicit lookup and `HTTPException(404)`. |
| 8 | `punch_in` | Check-then-insert race and no unique index: two simultaneous requests both pass `find_one` and both insert. Duplicate (emp_code, date) rows corrupt every analytic. | 20 parallel punch-ins -> several 201s (`test_punch_in_concurrent_exactly_one_201`). | Unique index `(emp_code, date)` created at startup; `insert_one` and `DuplicateKeyError` -> 409. The database is the only arbiter. |
| 9 | `PunchInIn` | No validation: seconds-looking values, floats, numeric strings and `true` are coerced; `status` accepts `ABSENT`, `LEAVE` or garbage (only presence statuses may be punched in). | `punched_at: 1783312500` (seconds), `"1783312500000"`, `true`, `-5`, `status: "HOLIDAY"` all accepted. | `EpochMs = StrictInt` in the range 1e11..4.1e12; `status: Literal[PRESENT, WFH, ON_DUTY]`. |
| 10 | `punch_in` response | Leaks `id` (the ObjectId as a string), which the contract says never appears; `punch_in` is a datetime serialised as an ISO string instead of epoch ms. | Response contains `"id": "6..."` and `"punch_in": "2026-07-06T09:30:00"`. | `serialize_attendance` builds the contract shape explicitly (no `_id`, epoch ms). |
| 11 | `create_employee` / `EmployeeIn` | No validation: bad `emp_code` format, malformed email, `shift_start == shift_end`, impossible `joined_on` (2026-02-30), blank names, malformed `HH:MM` all accepted. | 12 invalid bodies return 201 (`test_create_employee_validation_422`). | Pydantic constraints from the OpenAPI schema (patterns, lengths, real-calendar date check, shift difference). |
| 12 | `create_employee` | Same check-then-insert race, no unique index on `emp_code`. | 12 parallel creates -> multiple 201s (`test_concurrent_duplicate_employee`). | Unique index `emp_code`; `DuplicateKeyError` -> 409. |
| 13 | `create_employee` | `created_at = datetime.now()` is naive local time and is returned as an ISO string (not epoch ms); the client may also influence the document. | `created_at` is a string in the response (observed). | Server-set UTC, truncated to seconds, serialised as epoch ms; unknown client fields are ignored. |
| 14 | `list_employees` | `skip = page * page_size` (should be `(page-1) * page_size`): page 1 skips the first page of data. | `GET /employees?page_size=2` begins with EMP0003 instead of EMP0001 (observed). | `skip((page - 1) * page_size)`. |
| 15 | `list_employees` | `total` is `count_documents({})`, ignoring the `department` filter (R10: total reflects the filters). | `?department=DeptA` reports the whole collection size. | `count_documents(query)` with the same filter. |
| 16 | `list_employees` | No sort (contract: `emp_code` ascending, so pages are unstable); `page` / `page_size` unchecked: `page=0` is accepted (and `page=-1` gives a negative skip, which PyMongo rejects -> 500), `page_size=100000` loads everything. | `test_list_employees_bad_paging_422`. | `.sort("emp_code")`; `page >= 1`, `1 <= page_size <= 100` -> 422 otherwise. Index `(department, emp_code)` serves filter + sort. |
| 17 | `list_attendance` | Loads every matching document into memory (`list(find(q))`), sorts in Python, slices in Python: O(N) per request, hopeless at 100k records. Sort is by `date` only, with no `emp_code` tiebreak. | Latency and memory grow with the collection; equal-date rows come back in arbitrary order (`test_list_attendance_secondary_sort_emp_code`). | Database-side `sort(date desc, emp_code asc).skip().limit()`, backed by index `(date desc, emp_code asc)` (+ `(status, date, emp_code)` and the unique `(emp_code, date)` index). |
| 18 | `list_attendance` | Filters unvalidated: malformed dates, `date_from > date_to`, unknown `status`, out-of-range paging all pass through silently. | `test_list_attendance_validation_422` (7 cases). | Date type with real-calendar check, `Literal` status, explicit `date_from > date_to` -> 422. |
| 19 | `list_attendance` | Exposes `id`; returns raw datetimes (not epoch ms); legacy documents without `history` / `half_day` are returned as-is, violating the response schema. | `test_list_attendance_item_shape`, `test_list_attendance_legacy_doc_defaults`. | `serialize_attendance`: no `_id`, epoch ms, missing -> `[]` / `false` / 0. |
| 20 | `/health` | Always returns ok without touching MongoDB (contract: 200 only if Mongo answers, else 503). | Stop the database: `/health` still says ok. | `admin.command("ping")`; any `PyMongoError` -> 503. |
| 21 | Module setup | `MongoClient` without `tz_aware` (naive datetimes everywhere); 30 s default server-selection timeout makes requests hang when the DB is down; **no indexes at startup**; no handler for database errors (a stack-trace 500). | Any request with Mongo unreachable hangs for 30 s then 500s. | `tz_aware=True`, 5 s timeout, idempotent `ensure_indexes()` in the lifespan hook (retried from `/health`), `PyMongoError` handler -> 503. |

## Looked at and judged fine

- `load_dotenv()` with its default `override=False`: real environment variables already win, as the contract requires.
- Plain `def` endpoints with a synchronous driver: FastAPI runs them in a thread pool, so parallel requests work; correctness depends on atomic database operations, not on async.
- `doc.pop("_id")` after `insert_one`: correct in intent (the leak was the added `id`, item 10).
- The `MONGO_URI` / `MONGO_DB` fallbacks: only a local-development convenience; the grader injects both. Kept, documented in the code.
